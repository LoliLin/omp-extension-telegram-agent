# 审查结论

这个仓库**不需要推倒重写**。它已经抓住了群聊 Agent 降本的几个关键方向：不用 LLM 做路由、固定工具顺序、保持 append-only suffix、每个 Bot 独立 session、发送成功才算完成、视觉结果持久化缓存、合并并发 flush。

但若目标是“极致快速、极致低成本”，当前实现仍有四个结构性问题：

1. **`exposed` 同时承担“已经消费”和“当前上下文可见”两种状态，导致 compaction 后重放旧历史。**
2. **每次 flush 都扫描该群全部历史，运行时间会随数据库寿命线性增长。**
3. **输入只按消息条数限制，不按 token 预算限制，40 条消息仍可能远超上下文。**
4. **缓存 epoch 依赖人工版本号，且不会真正隔离旧 session；缓存可见配置没有完整 fingerprint。**

此外，当前文档中的约 **90% cache hit rate** 是一个有价值的局部实验结果，但还不能作为生产环境成本结论：它按 provider run 统计，不按“成功公开回复”统计；而且命中 token 本身仍有成本，稳定 prefix 越大，命中率甚至可能上升而总成本同时上升。仓库给出的数据是 734,208 个 cache-read token、81,659 个 miss token，算术上确实约为 90%，但该实验只有 50 次运行，且本次静态审计没有在相同环境复跑。([GitHub][1])

我检查了以下资料：

# 二、哪些东西应该 Pi 插件化

这里需要先区分两种“插件化”：

* **正确的插件化**：通过固定、显式、有序的 `extensionFactories` 把 Telegram 与 Pi 的适配逻辑放进 Pi 生命周期和 provider request hooks。
* **不适合的插件化**：让 Pi extension 自己启动 Telegram polling、管理长连接、数据库和整个 daemon。

Pi 官方文档明确提示 extension factory 可能在没有活跃 session 的情况下运行，因此不应在 factory 中启动长期 socket、timer 或外部进程。([GitHub][3])

## 2.1 应保留在 Pi 外部的部分

以下实现不是“重复造轮子”，而是合理的应用层：

| 模块                                 | 判断         | 原因                               |
| ---------------------------------- | ---------- | -------------------------------- |
| Telegram polling / 多 Bot update 摄取 | 保留在 daemon | 属于长期外部 I/O 和进程生命周期               |
| SQLite canonical event log         | 保留在 daemon | Pi session 不是 Telegram 群消息的权威数据库 |
| 概率/HMAC 路由器                        | 保留         | 这是业务路由，而且不调用 LLM，成本设计正确          |
| Telegram `send` 的事务性提交             | 保留         | 只有 Telegram API 成功后才能认为公开回复完成    |
| daemon 与 TUI 分离                    | 保留         | 后台服务和交互界面生命周期不同                  |
| 每个 Bot 独立 Pi session               | 保留         | 防止 persona、对话历史和工具状态互相污染         |

尤其不应把多个 Bot 合并进一个共享 Pi session。可以共享稳定 prefix，但不能共享实际对话状态。

## 2.2 应重构为显式 Pi extension 的部分

### A. Telegram context adapter

当前仓库自行完成：

* 从数据库选择消息；
* 渲染 `#messageId`、sender、reply quote；
* 把文本作为 Pi user message 喂入；
* 再自行维护哪些 ID 对模型“可见”。

这部分中的**数据库选择和 cursor 管理**仍应留在 daemon，但“将结构化 Telegram 事件转换成 Pi context”的适配层应成为 extension：

* 使用 Pi custom message 的 `details` 保存 `chat_id`、`message_id`、`sender_id`、`reply_to_id`；
* 使用 `context` hook 决定送给 provider 的最终文本；
* 不要再从渲染后的自然语言中正则解析 message ID；
* compaction 后的可见 ID 应从结构化 metadata 恢复，而不是扫描文本语法。

Pi 的 custom message 可以携带结构化 `details` 并参与 LLM context；`context` hook 也能修改最终上下文。([GitHub][3])

### B. Provider payload cache observer

仓库已经有 cache telemetry 和 `messages_hash` 字段，但实际 `recordUsage` 并没有写入 `messages_hash`。换句话说，当前能够看到 token hit/miss，却不能可靠回答：

> 两次请求究竟在第几个 provider message、哪个 tool schema 或哪个 system token 开始分叉？

([GitHub][5])

Pi `before_provider_request` hook 能看到实际 provider payload，并可用于：

* system prompt hash；
* tools 数组 hash；
* 每条 provider message 的独立 hash；
* 完整 payload hash；
* 第一个 prefix divergence 的位置；
* provider/model/API/cache retention/session affinity。

这应做成一个固定加载的 `tg-cache-observer` extension。([GitHub][3])

### C. Assistant persistence policy

当前 Bot 只有调用 `send` 工具的内容才会公开发送到 Telegram，但模型仍可能生成未调用 `send` 的普通 assistant prose。此类内容不会出现在群里，却可能被 Pi session 持久化并进入后续 context，产生三类问题：

* 隐性 token 累积；
* 群聊公开状态和模型内部状态不一致；
* 后续模型可能把未公开内容当成已经说过的话。

应通过 `message_end` 或 `context` extension：

* 保留必要的 tool-call/tool-result 链；
* 保留已提交 `send` 的规范表示；
* 删除或压缩没有公开发送的 assistant 文本；
* 明确加入一个固定的 `silence`/`no_send` 终止表示，而不是依赖空白 prose。

Pi 的 `message_end` handler 可以在消息落盘前替换最终消息。([GitHub][3])

### D. Compaction policy

仓库已经通过 extension hook 实现了一部分 compaction，所以方向正确，但目前 compaction 逻辑与 `BotRuntime`、数据库状态和主模型配置耦合较紧。应该拆成明确的 `tg-compaction` extension，输入和输出均为结构化状态：

```ts
interface TelegramCompactionState {
  consumedSeq: number;
  visibleMessageIds: number[];
  unresolvedReplies: number[];
  participants: Record<string, string>;
  durableFacts: string[];
}
```

不要让 compaction extension 决定 Telegram 的 ingestion cursor；它只能改变 Pi 当前 context。

### E. 通用工具

`search` 和 `run_js` 具有明显的通用 Pi 工具属性，可以拆成独立 extension/package。`send` 则仍然是 Telegram domain tool。

不过，当前通过 `customTools` 向 Pi 注册固定工具并不是绕过 Pi；这是 Pi SDK 的正式能力。应继续保持：

* 显式工具列表；
* 固定顺序；
* 固定 schema；
* 禁止按单次请求动态增删工具。

([GitHub][6])

推荐的结构是：

```ts
const extensionFactories = Object.freeze([
  makeTelegramContextExtension(deps),
  makeTelegramCompactionExtension(deps),
  makeCachePayloadObserverExtension(deps),
  makeAssistantPersistencePolicyExtension(deps),
]);

const resourceLoader = new DefaultResourceLoader({
  noExtensions: true,       // 禁止任意目录自动发现
  extensionFactories,       // 只加载受信且顺序固定的扩展
});

await createAgentSession({
  resourceLoader,
  noTools: "builtin",
  customTools: fixedOrderedTools,
  // ...
});
```

这是结构示意，不是可直接粘贴的完整 patch。关键点是：**插件化，但不动态化**。扩展顺序本身也是 cache-visible configuration，必须进入 fingerprint 和 golden test。

# 三、最高优先级的成本与缓存问题

## P0-1：`exposed` 混用了两种完全不同的语义

当前 `exposed_ids` 同时表示：

1. 这条 Telegram 消息已经被该 Bot 消费，不应再次处理；
2. 这条消息目前仍然存在于该 Bot 的 LLM context 中，模型知道它的内容和 ID。

这两个集合不相等。

### 当前代码产生的错误行为

flush 时，代码会读取全部消息，排除 `exposed`，选择最多一批消息；由于 catch-up 限制而没有送给模型的旧消息，也会被标记为 exposed。于是：

* 模型从未见过这些消息；
* serializer 却可能认为模型已经见过，因此省略 reply quote；
* `reply_to` 校验也可能接受这些 ID。

([GitHub][7])

更严重的是，compaction 会清空 exposed，再从保留文本中正则解析少量 ID。所有已经消费、但没有保留在 compacted tail 中的历史消息会重新变成“fresh”。仓库测试甚至明确固化了这种行为：compaction 后会重新摄取大量较旧历史。([GitHub][7])

结果是：

* compact summary 已经总结旧内容；
* 紧接着又把旧消息逐条追加回来；
* 第一个 post-compaction 请求的 miss tokens 增加；
* 后续所有请求的 cache-read tokens 也永久增加；
* 长期群聊会周期性重复搬运历史。

### 应拆成三套状态

```text
consumed cursor
    Telegram 事件是否已经完成业务消费，单调递增，永不因 compaction 回退

visible context refs
    哪些 message ID 的内容目前实际存在于 LLM context

reply obligations
    哪些直接回复、mention 或等待处理的事件仍需要执行
```

建议最少引入：

```sql
CREATE TABLE message_events (
  ingest_seq INTEGER PRIMARY KEY AUTOINCREMENT,
  chat_id INTEGER NOT NULL,
  message_id INTEGER NOT NULL,
  revision INTEGER NOT NULL,
  kind TEXT NOT NULL,
  payload_json TEXT NOT NULL
);

CREATE INDEX message_events_chat_seq
  ON message_events(chat_id, ingest_seq);

CREATE TABLE bot_cursors (
  bot_id TEXT NOT NULL,
  chat_id INTEGER NOT NULL,
  consumed_seq INTEGER NOT NULL,
  PRIMARY KEY (bot_id, chat_id)
);
```

规则必须是：

* compaction 可以改变 `visible_message_ids`；
* compaction **绝不能**重置 `consumed_seq`；
* overflow 丢弃的消息可以被标成 consumed，但不能被标成 visible；
* `reply_to` 只能引用真正 visible 的 ID，或必须附带短 quote；
* edits、reply metadata enrichment、vision completion 都应作为不可变 delta event 追加。

### 本 Bot 自己发送的消息也有一个小缺口

发送成功后，代码会立即把新 Telegram message ID 标记为 exposed，以避免之后重新摄入自身回声。这个去重目的正确，但模型只见过 `send` tool-call 中的文本，未必见过 Telegram 返回的 `#messageId → 文本` 映射。

后续别人回复该消息时，serializer 可能因为该 ID 已经 exposed 而省略 quote，但模型未必能把 `#messageId` 映射回自己发过的内容。解决方式是在 tool result 或结构化 custom message 中持久化：

```json
{
  "sent_message_id": 12345,
  "text_hash": "...",
  "reply_to_message_id": 12340
}
```

([GitHub][7])

---

## P0-2：每次 flush 都扫描完整群历史

当前 flush 路径会读取该 chat 的全部消息，然后在 JavaScript 中根据 `exposed_ids` 过滤；`exposed_ids` 又以完整 JSON 数组形式整块更新。([GitHub][7])

设群里累计有 (N) 条消息、某 Bot 新收到 (k) 条消息：

* 目标复杂度应接近 (O(k))；
* 当前读取复杂度接近 (O(N))；
* exposed 状态写入也会随已处理 ID 数量增长。

这意味着即使 LLM 完全不调用，单纯判断“有没有新消息”也会越来越慢。

### 正确查询方式

```sql
SELECT *
FROM message_events
WHERE chat_id = ?
  AND ingest_seq > ?
ORDER BY ingest_seq
LIMIT ?;
```

`consumed_seq` 更新必须与本轮选取/处理结果在事务中提交。

建议性能验收不是“本地感觉很快”，而是：

* 构造一个含 100 万条历史事件的 chat；
* 每次新增 10 条消息；
* flush 扫描行数不超过 `10 + 小常数`；
* p95 flush preparation latency 不随总历史量增长；
* `EXPLAIN QUERY PLAN` 必须命中 `(chat_id, ingest_seq)` 索引。

此外，`raw_updates`、`agent_events` 和 `llm_runs` 需要 retention/归档策略，否则即使主查询修正，数据库和维护操作仍会无限增长。

---

## P0-3：40 条消息不是 token budget

当前 catch-up 主要按消息数限制，而不是按模型输入 token 限制。serializer 允许动态消息内容达到较大的 codepoint 上限；按仓库自己的 32,768 codepoint 边界计算，40 条消息的理论上限约为：

[
40 \times 32768 = 1,310,720\ \text{codepoints}
]

这还不包括 sender、reply quote、metadata、system prompt、tools 和已有 session。([GitHub][8])

对中文、代码、URL 和 Unicode 文本，`字符数 ÷ 4` 不是可靠 token 估算。

### 应使用分层 token packing

优先级建议：

1. 当前直接 reply / mention；
2. 尚未完成的 reply obligation；
3. 最新普通消息；
4. 更早的背景消息；
5. 可省略的附件描述和 metadata。

预算应显式计算：

```text
available_suffix_budget =
    model_context_window
  - current_session_tokens
  - static_system_and_tools_tokens
  - output_reserve
  - reasoning_reserve
  - expected_tool_followup_reserve
  - safety_margin
```

还需要：

* 单条消息硬 token 上限；
* 截断时写入稳定标记，例如 `[truncated original_chars=...]`；
* 长代码、网页内容和搜索结果单独限额；
* packing 结果记录到 telemetry；
* direct reply 再长也不能挤掉整个对话，可保留头尾或先做确定性摘要。

这项修改同时改善：

* provider rejection；
* 首 token latency；
* miss token；
* cache-read token；
* compaction 频率。

---

## P0-4：`CACHE_SCHEMA_VERSION` 不是真正的 context generation

当前初始化顺序大致是：

1. `runtime.init()` 尝试恢复最近 Pi session；
2. 创建 `AgentSession`；
3. daemon 之后才检查 cache schema；
4. `noteSchemaBump()` 只更新内存中的 epoch 数字。

([GitHub][7])

因此，schema bump 能给 telemetry 换一个 epoch 标签，但不会：

* 创建新 session；
* 清除旧序列化格式的历史 user messages；
* 清除旧工具调用记录；
* 验证 persona、catalog、tool schema 是否与旧 session 匹配。

这不一定会让 provider 错误命中旧 prefix——system prompt 改变通常自然会产生 miss——但它**不能保证文档所暗示的“新 context epoch”隔离语义**。尤其当 serializer grammar 或 tool protocol 改变时，旧格式消息仍留在 session 中。

### 应改成内容寻址 fingerprint

```ts
const contextFingerprint = sha256(canonicalJson({
  piVersion,
  provider,
  api,
  model,
  reasoningEffort,
  cacheRetention,

  commonPromptSha256,
  personaSha256,
  serializerVersion,
  compactionPromptSha256,
  stickerCatalogSnapshotSha256,

  tools: orderedTools.map(t => ({
    name: t.name,
    description: t.description,
    parameters: t.parameters,
  })),
}));
```

在调用 `continueRecent()` 之前读取 session manifest：

```sql
CREATE TABLE bot_session_manifest (
  bot_id TEXT PRIMARY KEY,
  session_id TEXT NOT NULL,
  session_file TEXT NOT NULL,
  context_fingerprint TEXT NOT NULL,
  created_at INTEGER NOT NULL
);
```

fingerprint 不同则：

* 默认新建 session；
* 或运行一个显式、可测试的 migration；
* 绝不能只改 telemetry epoch 后继续恢复旧 transcript。

手工 `CACHE_SCHEMA_VERSION` 可以保留为强制失效开关，但不应再是唯一判据。

# 四、会降低 cache reuse 或增加总成本的其他设计

## P1-1：persona 位于公共协议之前

当前 system prompt 的构造顺序是 persona 在前，公共协议和工具使用规则在后。([GitHub][9])

对 DeepSeek 这类从请求开头进行 exact-prefix 匹配的缓存，只要不同 Bot 的 persona 从第一个 token 开始不同，位于其后的公共协议就无法形成跨 Bot 公共前缀。([DeepSeek API Docs][4])

建议顺序：

```text
1. 所有 Bot 完全相同的协议和安全规则
2. 完全相同的输出/send 约束
3. persona
4. Bot 特有能力
5. 小型动态/半动态信息
```

这不会保证所有 provider 都跨 session 共享缓存，因为 provider 可能按 API key、session ID 或内部 shard 隔离；但至少不会在 prompt 结构上主动阻断共享。

不要为了共享缓存而让多个 Bot 共用实际会话。只共享 prefix bytes。

---

## P1-2：把完整 sticker catalog 固定放进 system prompt

仓库会将最多约 120 个 sticker catalog 项目放进稳定 system prefix。([GitHub][10])

这种设计确实能提高命中率，但可能降低总体经济性：

* catalog token 每次都需要 cache read；
* catalog 越大，首 token 处理延迟通常越高；
* 任意 catalog 描述变化都会改变 system prefix；
* 实际大多数轮次可能完全不需要 sticker。

最优方案不是简单改成一个 `sticker_search` 工具，因为工具调用可能引入第二次 provider round。对“极致低延迟”更合适的是：

1. 在主调用前做本地确定性检索；
2. 根据本轮消息选出 top-K sticker；
3. 将候选放在动态 suffix 的末尾；
4. 只把 sticker 使用协议和工具 schema 留在稳定 prefix。

需要用真实 workload 比较：

```text
完整 catalog 的每轮 cached-read 成本
vs.
top-K 动态 miss 成本
vs.
tool-call 额外 provider round 成本
```

不要以 cache hit ratio 决定，应该以每次有效发送的总成本决定。

---

## P1-3：vision 阻塞主请求，且缺少 deployment-wide 预算

当前 runtime 会等待本批未缓存媒体的 vision 结果完成后，再发送主 LLM 请求；单 runtime 有并发限制和持久化缓存/进行中去重，这是正确的基础设计，但缺少全 deployment 的统一 semaphore、每轮媒体数量限制和成本预算。([GitHub][11])

多 Bot 群聊中，这会产生：

* 主回答延迟被最慢图片识别拖住；
* 多 Bot 同时准备上下文时，并发量按 Bot 数增长；
* 一批大量媒体可以在一次正常群聊触发中放大辅助调用成本；
* 即使最终模型选择不回复，vision 成本也已经发生。

建议：

* deployment-wide、按 `file_unique_id` 去重的 vision scheduler；
* foreground 每轮最多处理少量最相关媒体；
* direct reply/mention 的媒体优先；
* 普通 catch-up 图片默认不识别；
* 独立配置廉价 vision model；
* 设置每 chat/小时和全局日预算；
* 超出预算时序列化稳定占位符；
* vision 后到结果以不可变 `media_update #messageId` 追加，不能回写并改变已经进入 LLM 历史的旧消息。

最后一点对缓存尤其重要：**更新历史 message 的文本会破坏 append-only prefix；追加 delta event 不会。**

---

## P1-4：默认配置不是“成本优先”

当前配置允许继承 Pi 的 model/reasoning 设置，Pi SDK 没有更明确设置时的 thinking fallback 为 `medium`；同时目标仓库默认启用多种工具，compaction 配置也使用较大的 context/reserve。([GitHub][12])

对于低成本 Telegram 群聊 Agent，安全默认值应反过来：

```yaml
model: 显式指定，不继承开发机默认模型
reasoning: off
tools:
  send: true
  search: false
  run_js: false
vision:
  enabled: false
```

按需启用工具时，也应按**固定 Bot profile**启用，而不是每轮动态切换。工具集合变化会改变 provider tool schema，从而拆分 cache cohort。

Pi 的请求配置支持 `cacheRetention: none | short | long`，默认值为 `short`；仓库目前没有形成清晰的 provider-specific retention 控制面。Pi 也会把 session ID 传递给支持 cache/session affinity 的 provider，但这不等于应用已经选择了最合适的 retention 策略。([GitHub][13])

建议增加：

```ts
type CachePolicy = {
  retention: "none" | "short" | "long";
  affinityScope: "session" | "bot" | "deployment";
};
```

但必须由 provider adapter 做 capability mapping。DeepSeek 的缓存是自动进行的，某些接口并不接受 OpenAI/Anthropic 风格的显式 retention 参数，不能无条件透传。([DeepSeek API Docs][14])

---

## P1-5：compaction 使用主 Bot 模型，而不是独立廉价模型

代码中的 compaction 调用使用当前 Bot 的 `this.model`，设置 `cacheRetention: none`、`maxTokens: 4096`。因此即使注释或设计语言将其称为 auxiliary summarization，实际计费模型仍然是主 Bot 模型。([GitHub][7])

改进方向：

1. 显式配置 `compactionModel`；
2. 默认选择更廉价、更快的模型；
3. 先做确定性结构化压缩，只对无法结构化的信息调用 LLM；
4. summary 只保留：

   * 未完成承诺；
   * 当前讨论主题；
   * 关键事实；
   * 重要参与者映射；
   * 必要 message ID；
5. 不要总结已经无业务价值的群聊闲聊；
6. compaction 触发条件应基于边际成本，而不是只有固定 token 阈值。

合理触发条件可以表示为：

[
\text{expected future cached-read savings}

>

\text{compaction cost}
+
\text{post-compaction cache miss cost}
]

---

## P1-6：搜索结果可能向 context 注入 8,000 字符并增加一次模型轮次

搜索/fetch 工具允许返回较长文本，单次结果可达到约 8,000 字符，并通常需要模型在 tool result 后再运行一轮。([GitHub][15])

对群聊 Agent，这类工具应默认关闭。启用时至少需要：

* token 上限而非字符上限；
* 去重和 boilerplate removal；
* 只返回相关段落；
* 记录 tool-call 后续 provider round；
* 统计“搜索调用后最终没有公开发送”的浪费率；
* 搜索结果只存在于 suffix，不能进入 system prompt。

## P1-7：cache telemetry 还不足以定位 miss

文档描述了 ordered provider-message hashes，但数据库虽然有 `messages_hash` 字段，runtime 记录 usage 时没有填充它。([GitHub][1])

建议每次请求记录：

```json
{
  "provider": "...",
  "model": "...",
  "api": "...",
  "session_id_hash": "...",
  "cache_retention": "...",

  "system_hash": "...",
  "tools_hash": "...",
  "message_hashes": ["...", "..."],
  "full_payload_hash": "...",

  "input_cache_hit_tokens": 0,
  "input_cache_miss_tokens": 0,
  "output_tokens": 0,

  "trigger_message_id": 0,
  "public_send_count": 0,
  "vision_calls": 0,
  "tool_followup_rounds": 0
}
```

为了避免保存敏感群聊内容，hash 可使用 deployment-local HMAC，而不是普通 SHA-256。

最有用的调试字段不是只有总 hash，而是：

```text
first_divergent_segment
first_divergent_message_index
first_divergent_byte/token offset
```

否则两个 payload hash 不同，只能知道“不同”，不能知道为什么不同。

# 五、较低优先级但应修复的问题

## P2-1：同一 Telegram 消息存在重复路由窗口

多 Bot poller 场景下，同一消息可能先以 `inserted` 状态触发一次路由，之后另一个 Bot 补齐 `reply_to_sender_id` 等字段时又以 `enriched` 状态触发一次路由。第一次可能按概率选中 Bot，第二次又可能被识别为直接 reply，从而产生重复启动或一次额外无效 flush。

需要持久化 routing claim：

```sql
CREATE TABLE routing_claims (
  chat_id INTEGER NOT NULL,
  message_id INTEGER NOT NULL,
  bot_id TEXT NOT NULL,
  route_version INTEGER NOT NULL,
  status TEXT NOT NULL,
  PRIMARY KEY (chat_id, message_id, bot_id, route_version)
);
```

enrichment 只有在以下条件同时满足时才允许重新路由：

* enrichment 实质改变了直接 reply/mention 结论；
* 尚无已执行 claim；
* 尚未产生公开 send；
* 使用新的 route version 并保证幂等。

## P2-2：消息编辑应该是 delta，不应原地改历史

一条已经进入模型 context 的 Telegram message 如果后来被 edit，原地修改 canonical row 会造成两个问题：

* consumed cursor 不会自然重新发送；
* 若尝试回写旧 Pi message，又会破坏 append-only cache prefix。

应追加：

```text
[message_edit #123]
new text...
```

而不是修改已发送给 provider 的旧 user message。

## P2-3：日志和 telemetry 缺少长期 retention

`raw_updates`、agent events、LLM runs、message history 都会持续增长。结合当前全历史扫描，这既是磁盘问题，也是查询性能问题。修复 cursor 后仍应加入：

* 按时间或数量归档；
* 可配置 telemetry retention；
* periodic `VACUUM`/checkpoint 策略；
* 单 chat 数据量监控；
* 删除 Bot 时清理关联状态。

## P2-4：测试很多，但 CI 没有执行核心测试

仓库测试目录覆盖面较广，package scripts 也定义了测试和 TypeScript 检查；但现有 GitHub Actions 主要是文档 Pages，没有看到对 `bun test`、`tsc` 和 cache golden 的持续集成。([GitHub][2])

尤其需要加入以下回归测试：

```text
compaction_never_replays_consumed_events
overflow_messages_are_consumed_but_not_visible
reply_to_requires_visible_reference_or_quote
fingerprint_change_rotates_session
provider_payload_hash_is_deterministic
tool_order_change_changes_fingerprint
million_event_history_uses_bounded_index_scan
assistant_prose_without_send_is_not_in_next_context
global_vision_budget_is_enforced
edit_is_append_only_delta
```

# 六、文档、注释与代码之间的三处不一致

静态审计中有三处需要以代码行为为准：

### 1. “新 cache epoch”不等于新 context

文档倾向于把 schema bump 描述成新 epoch，但代码只在 session 恢复后更新一个 epoch 数字，没有创建新 session，也没有迁移 transcript。([GitHub][16])

### 2. “辅助 compaction 模型”实际仍是主模型

compaction 调用传入的是 `this.model`。除非部署主模型本身就是廉价模型，否则不能把它视为独立 cheap summarizer。([GitHub][7])

### 3. 文档声称有 provider message hash，实际没有落库

schema 有字段，设计文档也描述了它，但 usage 写入路径没有填充。([GitHub][5])

这些不一定是功能 bug，但会让成本分析产生错误信心。

# 七、建议的目标架构

```text
Telegram Pollers
       │
       ▼
Immutable Message Event Log
       │
       ├── deterministic router
       ├── durable routing claims
       └── per-bot consumed cursor
       │
       ▼
Batch Selector + Token Packer
       │
       ├── direct reply obligations first
       ├── global vision budget
       └── local sticker retrieval
       │
       ▼
Pi Adapter
       │
       ├── tg-context extension
       ├── tg-compaction extension
       ├── cache-payload-observer extension
       └── assistant-persistence-policy extension
       │
       ▼
AgentSession
       │
       ▼
Telegram send tool
       │
       └── commit sent_message_id / cursor / routing claim
```

核心不变量：

1. Telegram event log append-only；
2. consumed cursor 单调递增；
3. Pi context 在一个 compaction generation 内 append-only；
4. compaction 只改变 context，不改变 ingestion cursor；
5. 所有 cache-visible 内容都有 fingerprint；
6. provider payload 可以按段重现和比较；
7. 只有成功的 Telegram send 才计为 useful reply。

# 八、按收益排序的整改顺序

## 第一阶段：先让测量可信

1. 实现 `before_provider_request` payload segment hash；
2. 补齐 `messages_hash` 落库；
3. 增加 `public_send_count`、tool follow-up、vision、compaction 成本；
4. 把 cache golden、`bun test`、`tsc` 加进 CI；
5. 固定 Pi、Bun 和 provider adapter 版本。

没有这一步，后续优化可能只是“命中率看起来更高”。

## 第二阶段：修复状态模型和长期性能

1. 引入 immutable `ingest_seq`；
2. 用 per-bot cursor 替代全表扫描；
3. 拆分 consumed、visible、reply obligations；
4. 禁止 compaction 重置 consumed cursor；
5. edits/enrichment/vision 使用 append-only delta；
6. 加 routing claim 幂等。

这是最重要的一组重构。

## 第三阶段：控制每次调用的绝对 token

1. token-aware batch packing；
2. 单消息 token cap；
3. reasoning 默认 off；
4. 默认只保留 `send`；
5. compaction 使用廉价独立模型；
6. search/run_js/vision 默认关闭；
7. 加 provider-specific cache retention。

## 第四阶段：优化 prefix geometry

1. 公共协议移到 persona 前；
2. fingerprint 所有 cache-visible 配置；
3. sticker catalog 改为本地 top-K；
4. 固定工具 cohort；
5. 避免未公开 assistant prose 持久化；
6. 将 context adapter 和 payload observer extension 化。

# 九、应该用什么指标，而不是只看 cache hit rate

核心指标应是：

[
\text{cost per useful public reply}
]

其中包括：

```text
主请求 cache-miss input
+ 主请求 cache-read input
+ output/reasoning
+ 工具 follow-up provider rounds
+ vision
+ search/fetch
+ 摊销后的 compaction
```

至少同时跟踪：

* `provider_calls / useful_send`
* `cache_miss_tokens / useful_send`
* `cache_read_tokens / useful_send`
* `output_tokens / useful_send`
* `vision_calls / useful_send`
* `tool_followup_rounds / useful_send`
* `compaction_cost / useful_send`
* `silent_agent_runs / routed_runs`
* `accepted_route → Telegram send commit` 的 p50/p95/p99
* `DB rows scanned / flush`
* 按消息间隔分桶的 cache hit：`<1m`、`1–5m`、`5–30m`、`>30m`
* 按 persona/tool profile/provider/model 分 cohort 的命中率

一个重要反例是：

> 在每个 system prompt 中加入十万 token 的固定内容，cache hit rate 可能接近 100%，但每轮 cached-read token、延迟和总费用都会显著增加。

因此，应优化的是**缓存几何结构**：

1. 公共 prefix 有多长；
2. 动态 suffix 有多小；
3. prefix 保留多久；
4. 每个有效回复需要几次 provider call；
5. cached-read 的绝对 token 数是多少。

# 十、当前实现中值得保留的设计

以下设计符合低成本群聊 Agent 的目标，不应在重构中丢失：

* 使用确定性概率/HMAC 路由，而不是先调用一个 LLM router；
* 每 Bot 独立 session；
* 固定 tool order、schema hash 和 cache golden；
* 禁用 Pi 内置 coding tools；
* `send` 成功后才完成 Telegram 侧提交；
* 固定、简短的 tool acknowledgement/termination；
* vision 的持久化缓存、进行中去重和不盲目重试；
* busy/cooldown/coalescing；
* daemon 与 TUI 分离；
* 对 TinyFish/fetch 等外部结果设置体积和超时限制；
* 已有较丰富的测试文件。([GitHub][17])
