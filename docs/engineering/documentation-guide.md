# 文档写作规范

## 原则

文档是工程接口。写到让一个没有上下文记忆的读者（人或 LLM）能做出正确的改动并验证它。

## 一篇好文档要回答

1. **目的** — 这篇文档为什么存在
2. **范围** — 管什么、不管什么
3. **权威来源** — 这个事实的真正出处在哪里
4. **Invariant** — 什么必须始终成立
5. **接口** — 输入、输出、归属、依赖
6. **流程或决策** — 该做什么 / 当时选了什么
7. **例子** — 具体的正常 case 和边界 case
8. **验证** — 怎么证明这个陈述 / 流程是对的
9. **更新触发条件** — 哪类代码 / 产品变化要求这篇文档跟着改
10. **链接** — runbook、测试、代码入口

## 为检索优化

- 文件名和 ID 稳定；标题直白，不抖机灵。
- 答案放在搜索词会命中的标题附近。
- 归属 / 边界用表格，流程用编号步骤。
- 段落短、只写事实；文档里出现确切的 API / 包名 / 关键字。
- 重要信息不要只存在于截图里。

## 分清文档类型（生命周期不同，不要混）

- **Architecture**：稳定结构与 invariant（`docs/architecture.md`）
- **Guide**：流程与操作规范（`docs/engineering/`）
- **Runbook**：可重复的运维操作（`docs/runbooks/`）
- **Reference**：确切的接口语义（`docs/cache.md` / `docs/data-model.md` / `docs/testing.md`）
- **User guide**：面向用户的双语文档（`docs/user-guide/`）
- **AGENTS.md**：高信号路由、坑、命令

开发过程状态不单独建文档：追溯靠 git 历史（原子提交 + 清晰 message）。

## 避免重复

一个事实只有一个权威归属，其余文档链接过去。

坏：三篇文档各抄一遍当前路由状态机。
好：`architecture.md` 拥有状态机，其余链接到对应小节。

## 规范用词

- **MUST** = 硬 invariant；**SHOULD** = 有正当理由才可违反的默认；**MAY** = 可选。
- 能写出可观察规则时，不用“通常”“正确”“健壮”“干净”这类词。

## 写出能暴露歧义的例子

行为类文档覆盖：正常 case、非法输入、边界值、重试 / 超时 / 失败、并发 / 幂等（相关时）、兼容 / 迁移（相关时）。

## 让 LLM 写 / 改文档时

1. 给它文档类型和读者。
2. 指明它可以依据的权威代码 / 文档。
3. 说清什么变了、什么没变。
4. 要求区分已验证事实和假设。
5. 要求链接权威文件而不是复制细节。
6. 要求先找出矛盾 / 过期段落再动笔。
7. 对照代码和测试 review 文档 diff，不只看文笔。

## Review 清单

- 每条规范性陈述在当前代码里都成立吗？
- 有单一权威来源吗？
- 新读者能确定归属和下一步动作吗？
- 边界 case 和失败语义写清楚了吗？
- 命令可以直接复制粘贴、且是规范命令吗？
- 链接是相对 / 稳定的吗？
- 这次改动引入了重复知识吗？
- 有哪条纯文字规则可以改成机械检查（测试 / lint / schema）？
